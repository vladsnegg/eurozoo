# ПРОМПТ ЭТАПА 10 — Тестирование, покрытие и исправление ошибок

## 1. РОЛЬ
Ты — QA-инженер и разработчик, устраняющий дефекты по причинам, а не по симптомам. Тебе запрещено «делать тесты зелёными» ослаблением проверок.

## 2. КОНТЕКСТ
Функционал завершён (этапы 1–9). Цель этапа — доказать, что система работает в реальных сценариях, и устранить найденное.

## 3. ТЕКУЩАЯ АРХИТЕКТУРА
Vitest (unit), Supertest + Postgres (api), Playwright (e2e), axe, отдельная тестовая БД.

## 4. РЕЗУЛЬТАТЫ ЭТАПОВ 0–9
Все модули реализованы; есть базовые тесты; реальные данные; UI доведён.

## 5. ЦЕЛЬ
Покрытие и стабильность по порогам XII, отсутствие известных дефектов в пользовательских путях, воспроизводимые тесты с нуля.

## 6. ТЕХНИЧЕСКОЕ ЗАДАНИЕ
1. Инвентаризация тестов: что есть, чего нет, где `.skip`/`.only`, где тесты «для галочки» (без assert).
2. Unit: сервисы, мапперы, парсер поиска, ранжирование, валидаторы, layout-хелперы; ≥ 80% в сервисах.
3. DB: все CHECK, каскады, уникальности, R1–R6 (минимум 2 кейса на правило), идемпотентность сида.
4. API: каждый маршрут — happy + 400/401/403/404/409/422/429 (где применимо); контракт zod; пагинация/сортировка/whitelist.
5. E2E: 8 сценариев из XII.2 на двух вьюпортах; стабильность (без flaky) — 3 прогона.
6. A11y: axe на 10 страницах; 0 critical/serious.
7. Perf: замеры p95 поиска/каталогов/графа; LCP/CLS.
8. Дефекты: завести список, воспроизвести, найти причину, исправить, добавить регрессионный тест; не закрывать без теста.
9. CI: полный прогон на PR; отдельный job e2e с артефактами (trace/screenshot при падении).
10. Отчёт `docs/QA-REPORT.md`: матрица покрытия, результаты, найденные/исправленные дефекты, остаточные риски.

## 7. ЗАДАЧИ
1. Прогнать всё, зафиксировать базовую линию.
2. Дописать недостающие тесты по приоритету: безопасность → данные → поиск → UI.
3. Исправить дефекты, каждое исправление — с тестом.
4. Убрать `.skip`, мёртвые тесты, `console.log`, `any`.
5. Проверить тесты на чистой БД (`migrate reset` + seed).
6. Обновить `docs/QA-REPORT.md`.

## 8. ТЕХНОЛОГИЧЕСКИЕ ОГРАНИЧЕНИЯ
- Не менять требования/поведение ради тестов.
- Не использовать `sleep` вместо ожиданий Playwright.
- Не мокать то, что должно проверяться интеграционно (БД, права).
- Не увеличивать таймауты «чтобы прошло».

## 9. КАЧЕСТВО
- Тест проверяет поведение, а не реализацию.
- Один тест — одна причина падения (по возможности).
- Фикстуры явные, без скрытых зависимостей между тестами.
- Тесты независимы и могут идти в любом порядке.

## 10. БЕЗОПАСНОСТЬ
- Обязательные тесты: 401/403 на всех защищённых маршрутах, rate limit логина/поиска, отсутствие секретов в ответах, cookie-флаги.
- Проверить, что ошибки не содержат стектрейсов в prod-режиме.

## 11. GITHUB
Ветка `stage/10-testing`; PR с `QA-REPORT.md` и артефактами CI; запрещено мержить с падающими тестами.

## 12. PRE-FLIGHT
Проверить: этапы 4–9 приняты; тестовая БД доступна; `TEST_DATABASE_URL` корректен; нет незакоммиченных изменений.

## 13. СОВМЕСТИМОСТЬ
Не менять публичные контракты. Если найден баг в контракте — зафиксировать и согласовать, не «тихо» ломать.

## 14. ТЕСТЫ
Это и есть содержание этапа. Критерии: см. XII.1–XII.3.

## 15. КРИТЕРИИ ПРИЁМКИ
- [ ] Unit ≥ 80% в сервисах; критичные утилиты — 100%.
- [ ] API: каждый маршрут покрыт happy+error.
- [ ] E2E: 8/8 зелёные, 3 прогона без flaky.
- [ ] R1–R6 покрыты.
- [ ] Нет `.skip`/`.only`; нет `any` в новом коде.
- [ ] `migrate reset && seed && test` — зелёные с нуля.
- [ ] `QA-REPORT.md` заполнен.
- [ ] Отчёт по шаблону.

## 16. ОТЧЁТ
По шаблону + матрица покрытия + список дефектов (найден/исправлен/тест) + остаточные риски.

## 17. ЗАПРЕЩЕНО
- Ослаблять/удалять тесты, увеличивать таймауты без причины.
- Мокать БД в интеграционных тестах.
- Игнорировать flaky-тесты.
- Закрывать дефект без регрессионного теста.
- Менять поведение системы под тест.
