# ПРОМПТ ЭТАПА 5 — Поиск, фильтрация и навигация по знаниям

## 1. РОЛЬ
Ты — инженер поиска и UX-навигации. Твой критерий успеха — пользователь находит знание за 1–2 запроса и попадает в связи, а не в тупик.

## 2. КОНТЕКСТ
EuroZoo Atlas. Поиск — Postgres FTS + `pg_trgm` + синонимы. «Семантический» слой — онтологическое расширение запроса, без эмбеддингов (ADR-05).

## 3. ТЕКУЩАЯ АРХИТЕКТУРА
`mv_search_index` (этап 3), модуль `search` в api, страницы каталогов (этап 4), стратегия URL-состояния.

## 4. РЕЗУЛЬТАТЫ ЭТАПОВ 0–4
Каталоги работают; провенанс отображается; API стабилен; сид загружен.

## 5. ЦЕЛЬ
`GET /search` + `/search` + глобальный поиск в хедере: релевантные результаты по всем типам, фасеты, синонимы, фолбэк на нечёткое совпадение, «похожие объекты» и «связано с».

## 6. ТЕХНИЧЕСКОЕ ЗАДАНИЕ
1. `GET /search?q&types&country&iucn&programCode&page&pageSize` → `{query, total, page, pageSize, groups[], facets[], suggestions[]}`.
2. Пайплайн: нормализация (`lower`, `unaccent`) → расширение по `search_synonym` (≤ 8 термов) → `websearch_to_tsquery('russian', ...) OR to_tsquery('english', ...)` → ранжирование:
   `score = ts_rank_cd(tsv, query) * 1.0 + similarity(title, q) * 0.6 + typeBoost + recencyBoost`, где `typeBoost`: zoo 0.15, species 0.15, program 0.10, country 0.05, organization 0.05; `recencyBoost ≤ 0.05`.
3. Фасеты: counts по типу, стране, IUCN, коду программы — отдельными CTE, только для найденного набора.
4. Suggestions: если `total = 0` — top-5 по `similarity(title, q) >= 0.3`.
5. `GET /entities/:type/:id/related?limit=8` — рёбра + структурные связи, группировка по предикату, приоритет редким.
6. `GET /entities/:type/:id/similar?limit=4` — R5/R6.
7. UI: `SearchInput` с debounce 300 мс и `AbortController`; страница `/search`; подсветка (`<mark>`, экранирование); группы; фасеты; пагинация; пустое состояние с подсказками; клавиатура (`/` — фокус, Esc — очистка, стрелки — навигация).
8. Кэш: синонимы и фасеты — LRU 60 с; результаты — `Cache-Control` только для одинаковых запросов (по ключу), не для авторизованных.
9. Оценка качества: `docs/SEARCH-EVAL.md` — таблица «запрос → ожидаемый top-3» ≥ 20 запросов (включая русские/латинские, опечатки, спецсимволы).

## 7. ЗАДАЧИ
1. Сервис поиска + SQL + тесты ранжирования.
2. Контроллер + DTO + коды ошибок.
3. Синонимы: сид (20+ пар), админ-CRUD — на этапе 7, здесь только чтение.
4. UI поиска и «связано с»/«похожие» на карточках.
5. Метрики: p95, пустые ответы, top-3 точность на eval-наборе.
6. Тесты: unit парсера/ранжирования, API, e2e сценарии.

## 8. ТЕХНОЛОГИЧЕСКИЕ ОГРАНИЧЕНИЯ
- Никаких LIKE '%...%' в горячем пути (кроме trigram-фолбэка).
- Никаких внешних поисковых сервисов.
- Лимит расширения — 8 термов; защита от «шума» стоп-слов.
- Спецсимволы запроса не должны ронять запрос (санитизация до `websearch_to_tsquery`).

## 9. КАЧЕСТВО
- Поиск объясним: в dev-режиме — `?debug=1` возвращает score-компоненты (без утечки внутренних id).
- Никаких магических порогов без комментария и теста.
- Подсветка не ломает HTML и не выводит сырой запрос пользователя без экранирования.

## 10. БЕЗОПАСНОСТЬ
- Rate limit: 30 запросов/мин/IP для `/search` (429 с `Retry-After`).
- Ограничение длины `q` (≤ 200 символов).
- Никакого SQL-конкатенирования; только параметры.
- Не логировать полные запросы пользователей дольше необходимого.
