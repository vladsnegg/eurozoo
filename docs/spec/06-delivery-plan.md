## IX.2. Детализация этапов

### ЭТАП 0. Аудит и ТЗ
- **Результат:** `docs/AUDIT.md` (доступ к репо, стек, структура, точка входа, зависимости, env, схема данных, что реализовано, техдолг, тесты, документация) и `docs/TZ.md` (скоуп, термины, ограничения, риски, критерии готовности).
- **Задачи:** проверить доступ (токен/SSH); клонировать; `git log --oneline`; карта каталогов; чтение `package.json`, `docker-compose*`, `.env.example`, `prisma/schema.prisma`; запуск существующих тестов; фиксация того, чего нет.
- **Запрещено:** удалять/переписывать код; делать выводы без доказательств; выдавать гипотезы за факты.
- **Приёмка:** каждый пункт аудита сопровождается путём к файлу/командой; противоречия с этим комплектом вынесены в «Reconciliation»; ТЗ подписано (чекбокс в PR).

### ЭТАП 1. Архитектура
- **Результат:** утверждённые `ARCHITECTURE.md`, `DOMAIN.md`, `schema.prisma` (черновик), `er.mmd`, реестр предикатов, ADR-файлы.
- **Задачи:** согласовать стек с аудитом (сохранить существующее, если совместимо); финализировать таблицы/связи/инварианты; описать API-контракты (zod); определить `entity_type`, `publish_status`, `source_type`; зафиксировать лимиты поиска/графа.
- **Приёмка:** ER валиден Mermaid; каждая сущность имеет PK/FK/ограничения; все связи из `01-concept-and-domain.md` покрыты; нет неразрешённых вопросов (список «Open questions» пуст или имеет владельца и срок).

### ЭТАП 2. Фундамент
- **Результат:** `pnpm dev` поднимает web+api; `docker compose up -d db`; `/health` 200; CI зелёный на пустом проекте; layout/header/footer/404/error.
- **Задачи:** workspace, tsconfig, eslint, prettier, turbo; env-валидация (zod) при старте — падать с понятной ошибкой; helmet/cors/cookies; логирование; базовые UI-компоненты; тестовая БД.
- **Приёмка:** чистая машина → 3 команды → приложение работает; `pnpm lint typecheck test` зелёные; секретов нет; README с шагами запуска.

### ЭТАП 3. Модель данных и knowledge core
- **Результат:** миграции всех таблиц; сид-фреймворк (JSON + валидация + идемпотентность); read-API каталогов; view-правила R1–R6 с тестами; `mv_search_index` и refresh.
- **Задачи:** Prisma schema + миграции + CHECK на уровне SQL (Prisma не всё умеет — raw SQL миграция); индексы; репозитории/сервисы; DTO; пагинация/фильтры; `data:check` (целостность, сироты, дубли, циклы таксонов); `data:stale`.
- **Приёмка:** `prisma migrate reset` + `db:seed` воспроизводимы; повторный сид не дублирует; правила R1–R6 возвращают ожидаемое на фикстурах; explain analyze ключевых запросов без seq scan на больших таблицах (сид ≥ 1000 зоопарков-заглушек для нагрузки? — нет: используем 30 реальных + генератор только в тестах).

### ЭТАП 4. Каталоги и карточки
- **Результат:** страницы `/zoos`, `/zoos/[slug]`, `/species`, `/species/[slug]`, `/taxonomy`, `/countries`, `/countries/[slug]`, `/cities/[slug]`, `/programs`, `/programs/[slug]`, `/organizations`, `/organizations/[slug]`, `/research`.
- **Задачи:** SSR-страницы, фильтры в URL, карточки, таблицы, бейджи IUCN, провенанс, «связано с», SEO, 404.
- **Приёмка:** каждый маршрут открывается на сиде; фильтры комбинируются; нет N+1 (проверка логами запросов ≤ 6 на страницу); мобильный вид без горизонтального скролла тела.

### ЭТАП 5. Поиск и навигация
- **Результат:** `/search` + глобальный поиск, фасеты, синонимы, suggestions/trigram-фолбэк, «похожие», пагинация.
- **Задачи:** SQL-ранжирование, кэш синонимов, отмена запросов, подсветка, фасетные счётчики, пустые состояния; тесты релевантности на наборе запросов.
- **Приёмка:** набор из 20 запросов даёт ожидаемый top-3 (таблица в `docs/SEARCH-EVAL.md`); p95 ≤ 400 мс; запрос с спецсимволами не роняет API; «тигр» находит зоопарки через связи.

### ЭТАП 6. Связи и граф
- **Результат:** `GET /graph`, `/graph` UI, блок «связано с», похожие объекты, маркировка inferred, экспорт PNG/ссылки.
- **Задачи:** BFS CTE, whitelist предикатов, лимиты, дедупликация узлов, layout ELK, панель узла, восстановление из URL.
- **Приёмка:** depth/типы/предикаты работают; нет дублей; цикл не вешает; 200 узлов рендерятся < 1.5 с; ссылка восстанавливает состояние.

### ЭТАП 7. Админка и авторизация

## XII. План тестирования

### XII.1. Уровни и критерии

| Уровень | Инструмент | Что покрывает | Порог |
|---|---|---|---|
| Unit | Vitest | сервисы, мапперы, валидаторы, парсер поиска, layout-хелперы | ≥ 80% строк в `apps/api/src/modules/**/service.ts` и `packages/shared` |
| DB/SQL | Vitest + pg | ограничения, каскады, view R1–R6, целостность рёбер | 100% правил R1–R6 и всех CHECK из V.2 |
| API | Supertest + Postgres | все эндпоинты, коды, пагинация, фильтры, RBAC, ошибки | каждый маршрут ≥ 1 happy + 1 error |
| Contract | zod shared | ответы соответствуют схемам | 100% публичных DTO |
| E2E | Playwright | 8 сценариев (ниже) | 100% зелёные, 0 console errors |
| A11y | axe-core в E2E | ключевые страницы | 0 critical/serious |
| Perf | скрипт + логи | p95 API, LCP/CLS | p95 ≤ 400 мс (поиск), ≤ 300 мс (каталоги) |

### XII.2. E2E-сценарии (обязательные)

1. Главная → поиск «тигр» → карточка вида → блок «где содержится» → карточка зоопарка.
2. Каталог зоопарков: фильтр по стране + сортировка + пагинация; URL сохраняется после reload.
3. Карточка вида: линия таксономии доходит до корня; переход по семейству показывает всех потомков.
4. Граф: открыть зоопарк → «в графе» → depth=2 → клик по узлу → «открыть карточку».
5. Админ: логин → создать зоопарк без источника → публикация запрещена (422) → добавить источник → публикация успешна.
6. RBAC: editor не видит «Пользователи» (403); viewer не видит `/admin`.
7. Ошибки: неизвестный slug → 404-страница; API 500 → error boundary с «Повторить».
8. Адаптив: 390×844 — каталог, карточка, граф, админ-форма без горизонтального скролла.

### XII.3. Критерии сдачи модуля

Модуль не принят, если: есть заглушки/`TODO` в пользовательском пути; не покрыт хотя бы один сценарий из спецификации; есть необработанный 500 в E2E; тесты отключены/ослаблены; данные выдуманы; отсутствует источник у опубликованного факта.

## XIII. GitHub-процесс

### XIII.1. Ветвление
- `main` — защищена: запрещён force-push, обязательны зелёные CI и ревью (минимум — само-ревью через PR).
- Рабочая ветка этапа: `stage/NN-slug` от актуальной `main`.
- Коммиты: Conventional Commits, атомарные; сообщение объясняет «что и почему».
- PR: шаблон (что сделано, как проверено, риски, скриншоты UI, чек-лист приёмки), squash-merge.
- Теги: `v1.0.0` на релизе.

### XIII.2. Параллельная работа агентов
- Один агент = один этап = одна ветка.
- Пересечение файлов запрещено: зоны (`apps/api/src/modules/<x>`, `apps/web/src/app/<x>`) закрепляются за этапом.
- Общие файлы (`prisma/schema.prisma`, `packages/shared`, `app.module.ts`, `layout.tsx`) меняются только через PR с пометкой `shared-change` и ревью владельца архитектуры.
- Перед началом: `git fetch && git rebase origin/main`; перед PR: rebase, прогон тестов.
- Миграции: одна миграция на PR; имя описательное; конфликт миграций решается пересозданием, не правкой применённой.

### XIII.3. Секреты и данные
- `.env` не коммитится; `.env.example` — фиктивные значения.
- Secret scanning в CI (`gitleaks`), запрет `git add -A` без проверки.
- Персональные данные не собираются; email пользователей — только для входа.

### XIII.4. Definition of Done PR
1. Код + тесты + документация.
2. `pnpm lint && pnpm typecheck && pnpm test && pnpm test:api` зелёные.
3. E2E затронутых сценариев зелёные.
4. Нет новых `TODO`/`FIXME` в пользовательских путях.
5. Обновлён `README`/`docs`, если изменился запуск/конфиг.
6. Отчёт по шаблону этапа.
7. Скриншоты (для UI) и примеры запросов/ответов (для API).
